# تحديث بن دول v2.2 — إلغاء الديون والتحليلات والاعتماد الإداري المبسط

## ما تغير

1. أزيلت من واجهة الموظف جميع حقول الدين، بما فيها **قيمة الدين المتبقي**. لم يعد يسمح الخادم بإضافة صف دين أو تحويل بنكي لتسديد حساب سابق.
2. أزيلت من واجهة المدير صفحات **فواتير غير مطابقة** و**العملاء والديون** و**تحليل الورديات** و**فلوشارت المطابقة**، وألغيت مسارات API المقابلة للجديد.
3. أصبحت **مطابقة** زرًا في **سجل الورديات**؛ يعرض نافذة مراجعة قصيرة، ثم يتطلب اختيار مربع التأكيد والضغط على **تأكيد الاعتماد**. المدير فقط من يستطيع تنفيذها.
4. لا يطلب النموذج الجديد **مبيعات الشبكة** أو **النقد المتبقي**؛ لذلك فإن الاعتماد **إداري على بيانات الوردية، وليس مطابقة نقد فعلية ولا إثباتًا لصحة العجز أو الفائض**. تم وقف احتساب ونشر العجز والفائض في عمليات الإصدار الجديد.
5. تظل أقسام المشتريات والأصناف خارج الجهاز والتحويلات البنكية وبيانات الصندوق والإيداع ومرفقات PDF/PNG/JPG الاختيارية.
6. حفظ سجل التدقيق، صلاحيات المدير، منع الاعتماد المكرر، المعاملة الواحدة، مفتاح منع تكرار الطلبات، التصدير PDF وCSV، وإنشاء ورديات متعددة في اليوم نفسه.

## خصوصية البيانات القديمة

لا تحذف حزمة التحديث أي عميل أو دين أو وردية قديمة أو اعتماد نقدي قديم من PostgreSQL. تبقى تلك البيانات للأرشفة والمراجعة المحاسبية. الواجهة الجديدة لا تتيح إنشاء ديون جديدة أو تعديل ورديات تعتمد على قيود الديون القديمة، كما لا تسمح بتمريرها إلى الاعتماد المبسط. عند الحاجة إلى تسوية الديون السابقة، احتفظ بنسخة من برنامج الإصدار 2.1 أو استعِن بمحاسب وخطة انتقال منفصلة. لا تستخدم حذف الجداول أو تحديثها يدويًا.

**لا يوجد ترحيل قاعدة بيانات جديد لهذا الإصدار**. ترحيل v2.1 حتى `20261030_03` مطلوب، ثم يصبح تشغيل `alembic upgrade head` آمنًا كفحص اعتيادي على قاعدة الاختبار. اختبار قاعدة PostgreSQL الحية يجب تنفيذه على نسخة مستعادة منعزلة قبل الإنتاج.

## طريقة التركيب على Windows — فوق مشروع v2.1 الحالي

المجلد الذي تستخدمه عادة:

```text
C:\Users\Dell\Downloads\Daily_Sales_Cash_Reconciliation_System (1)\Bin_Doul_Financial_System
```

1. أوقف Uvicorn بـ `Ctrl+C`. تحقق من نسخة PostgreSQL الاحتياطية ومن نسخة ملفات المشروع التي حفظتها.
2. احفظ حزمة التحديث `BinDoul_Update_v2_2.zip` في Downloads. تأكد أن ملف ZIP يحوي جذرًا باسم `Bin_Doul_Financial_System`.
3. فك ضغط الحزمة **داخل مجلد `Daily_Sales_Cash_Reconciliation_System (1)` الأب**، ووافق على استبدال ملفات الكود. **لا تمس `.env` أو قاعدة البيانات**؛ الحزمة لا تتضمن ملفات `.env` أو `frontend/dist`.
4. افتح PowerShell داخل جذر `Bin_Doul_Financial_System` وشغّل:

```powershell
npm --prefix frontend ci
npm --prefix frontend run build
```

5. افحص الترحيل الحالي من جذر المشروع:

```powershell
cd backend
.\.venv\Scripts\python.exe -m alembic -c shift_alembic.ini current
```

يُفترض أن يكون إصدار الترحيل `20261030_03 (head)`. إن لم يكن كذلك، **لا تنفّذ أي ترحيل إضافي على قاعدة بيانات الإنتاج قبل مراجعة السبب واستعادة نسخة اختبار أولًا**.

6. جهّز اختبارات الإصدار الجديد؛ السكربت التالي **لا يلمس قاعدة البيانات أو ملفات التطبيق**، بل ينقل فقط ثلاثة ملفات اختبارات v2.1 القديمة إلى `docs/v2_1_tests_archived` إن كانت موجودة:

```powershell
cd ..
backend\.venv\Scripts\python.exe scripts\prepare-v2_2-tests.py
```

7. شغّل الاختبارات على قواعد الاختبار المستقلة (وليس قاعدة الإنتاج):

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest shift_tests -q
```

8. شغّل الخادم:

```powershell
.\.venv\Scripts\python.exe -m uvicorn shift_app.main:create_app --factory --host 127.0.0.1 --port 8000
```

9. افتح `http://127.0.0.1:8000` واضغط `Ctrl+F5`، وسجّل دخول مدير. راجع القائمة، وجرّب أولًا على `bin_doul` التجريبية أو قاعدة اختبار مستقلة، **لا على قاعدة إنتاج مستخدمة للعمل الحقيقي**.

## سيناريو التحقق اليدوي

- سجّل دخول موظف: تأكد من عدم وجود قسم ديون أو حقل «قيمة الدين المتبقي» أو مبيعات شبكة أو نقد متبقٍ؛ أدخل مشتريات وتحويلًا بنكيًا دون رقم فاتورة أو مرفق، ثم سلّم وردية واستخدم «بدء وردية جديدة» لوردية أخرى بسند مختلف.
- سجّل دخول مدير: القائمة لا تحتوي «فواتير غير مطابقة»، «العملاء والديون»، «تحليل الورديات»، أو «فلوشارت المطابقة».
- افتح «سجل الورديات»، اضغط **مطابقة** على وردية غير معتمدة؛ تأكد أن **تأكيد الاعتماد** لا يتفعّل إلا بعد اختيار مربع التأكيد.
- بعد التأكيد، تتحول الوردية إلى «معتمدة» ولا يمكن اعتماد النسخة نفسها ثانيةً؛ تحقق من سجل التدقيق ومن PDF وCSV.
- لا تعتمد أو تحذف أو تصحّح بشكل تجريبي وردية مالية حقيقية.

## حدود التحقق

في بيئة إعداد الحزمة: اجتازت اختبارات Python الآلية **39 اختبارًا**، وتُخطِّي اختبار PostgreSQL الاختياري لغياب قاعدة اختبار فعلية. اجتازت ملفات TypeScript فحص الصياغة، لكن **لم ينجح تثبيت جميع حزم npm هنا** لأسباب الشبكة، ولذلك لم يُجرَ `tsc -b && vite build` كاملًا في بيئة التجهيز؛ يجب تنفيذ أمر البناء على جهاز Windows كما في الخطوات أعلاه. هذا ليس تصريحًا بأن التحديث اختُبر على قاعدة الإنتاج أو على خادم رسائل خارجي.
