# قاعدة البيانات وسلامة العمليات والنسخ الاحتياطي

## الكيانات

| الجدول | الوظيفة والعلاقات |
|---|---|
| users | المستخدمون وأدوارهم وتجزئات كلمات المرور؛ لا يحذف المستخدم المستخدم في معاملات |
| settings | صف واحد للمتجر والعملة والمنطقة الزمنية، وكذلك قفل تسلسل الكتابة |
| auth_sessions | تجزئات رموز جلسات تسجيل الدخول وحماية CSRF وانتهاء الصلاحية |
| login_throttles | محاولات الدخول وحدودها عبر جميع عمال API، حسب الحساب والمصدر |
| cash_sessions | جلسات الصندوق وأساس المبيعات والجرد والإصدار وعلاقة الترحيل مع الجلسة السابقة |
| customers | هوية العميل والهاتف والملاحظات |
| customer_debts | أصل الدين ونوعه وتاريخه واستحقاقه والعميل والجلسة عند البيع الآجل |
| debt_payments | كل دفعة مستقلة مرتبطة بالدين وجلسة التحصيل وطريقة الدفع |
| purchases | كل فاتورة مستقلة وطريقة دفعها وما إذا كان الدفع من الصندوق |
| cash_movements | دفتر الأثر النقدي؛ حركات يدوية ومصادر مرتبطة فريدة |
| closing_snapshots | نسخ إضافية ثابتة من اعتماد الإغلاق ومجاميعه وملاحظته |
| audit_logs | سجل إضافي ثابت للإنشاء والتعديل والإلغاء والإغلاق وإعادة الفتح |
| idempotency_records | مفتاح وبصمة واستجابة الطلب لمنع تكرار العملية لكل مستخدم |
| alembic_version | إصدار ترحيلات قاعدة البيانات |

الجداول المالية تستخدم مفاتيح خارجية بلا حذف متسلسل. جميع المبالغ `DECIMAL(18,2)`، والنص العربي NVARCHAR، والملاحظات الطويلة NVARCHAR(MAX) في SQL Server. المخطط الكامل والفهارس والقيود في `sqlserver-schema.sql` والترحيلات.

## حدود المعاملة والتزامن

كل عملية كتابة تبدأ بـ:

```sql
UPDATE settings SET revision = revision + 1 WHERE id = 1;
```

يمسك SQL Server قفل تحديث حصري لهذا الصف حتى Commit أو Rollback. لا تحصل العمليات على قفل دين أو جلسة ثم تبحث عن قفل المتجر؛ ترتيب القفل موحد. بعد القفل تعاد مراجعة المستخدم وحالته وصلاحيته ومفتاح الطلب ثم قواعد الدين أو الجلسة. لذلك لا يستطيع موظفان استهلاك الرصيد نفسه أو إضافة حركة بعد أن يغلق طلب آخر الجلسة.

هذا اختيار مقصود لنسخة المتجر الواحد والصندوق الواحد. يفضل الاتساق على تنفيذ عمليات مالية متوازية للصندوق نفسه؛ ليس تصميمًا لعدة فروع أو آلاف الصناديق.

تسجيل الأصل والحركة المولدة وسجل التدقيق واستجابة منع التكرار يحدث داخل معاملة SQLAlchemy واحدة. أي استثناء يلغي الجميع. لا توجد عمليات نجاح جزئي. تكرار المفتاح نفسه بالمحتوى نفسه يعيد الاستجابة السابقة حتى لو أغلقت الجلسة لاحقًا. المحتوى المختلف للمفتاح نفسه مرفوض. لا تُحذف مفاتيح المعاملات تلقائيًا، منعًا لإعادة تشغيل طلب مالي قديم.

تقارير القراءة تمسك قفل قراءة `HOLDLOCK` لصف إعدادات المتجر أثناء المعاملة لتبقى مجموعاتها متسقة معًا. إعدادات عزل SQL Server الافتراضية مناسبة مع هذا البروتوكول. لا تُستعمل `NOLOCK` لقراءة الأرقام المالية.

حماية إضافية بالقيود والفهارس: مبلغ موجب للديون والسداد والفواتير والحركات، افتتاح وجرد غير سالبين، أصل الدين متسق مع نوعه، طريقة الدفع صحيحة، وصندوق واحد وجلسة مفتوحة واحدة. تمنع Triggers تعديل وحذف سجل التدقيق أو لقطات الإغلاق حتى لو استُخدمت SQL خارج API. حساب التشغيل ينبغي ألا يمتلك صلاحية حذف المعاملات أصلًا.

يفرض API قيود المجاميع المشتركة بين الجداول، مثل حد السداد والمبيعات الآجلة؛ لا تُنفذ إدخالات مالية من برامج أخرى أو بتعديل الجداول يدويًا. عند الحاجة لترحيل بيانات خارجي يجب أن يلتزم بالخدمات والقفل نفسيهما. وجود SQL Server لا يعوض تجاوز طبقة القواعد المالية.

## صلاحيات قاعدة التشغيل

نفّذ الترحيلات بحساب تهيئة، ثم أنشئ حساب تشغيل مستقلًا موجودًا بالفعل في SQL Server وامنحه الدور الموجود في `runtime-permissions.sql`. لإنشاء المستخدم المرتبط بـLogin من SSMS:

```sql
USE DailySales;
GO
CREATE USER DailySalesApp FOR LOGIN DailySalesApp;
GO
```

أنشئ Login نفسه واختَر كلمة مروره من SSMS، أو استخدم حساب خدمة Windows قائمًا. لا تسجلها في نص SQL محفوظ. بدّل `.env` إلى حساب التشغيل بعد تطبيق الترحيلات، واحتفظ بحساب التهيئة لأوقات الترقية فقط. الدور المرفق لا يمنح CREATE أو ALTER أو DROP، ولا حذف جداول مالية، ولا تحديث سجلات التدقيق واللقطات.

## نسخة احتياطية كاملة

هذه أوامر تشغيل يقوم بها مسؤول SQL Server، ولا ينفذها التطبيق تلقائيًا. أنشئ مجلد النسخ على جهاز خادم SQL Server، وامنح **حساب خدمة SQL Server** الكتابة فيه. مسار النسخة يفسَّر على جهاز الخادم، وليس متصفح المستخدم.

مثال لنسخة جديدة باسم فريد، دون استبدال نسخة قائمة:

```sql
BACKUP DATABASE DailySales
TO DISK = N'D:\SQLBackups\DailySales_20261028_230000.bak'
WITH COPY_ONLY, CHECKSUM, STATS = 10;
GO
RESTORE VERIFYONLY
FROM DISK = N'D:\SQLBackups\DailySales_20261028_230000.bak'
WITH CHECKSUM;
GO
```

استبدل التاريخ والوقت باسم فريد لكل تشغيل. `COPY_ONLY` مناسب لنسخة كاملة يدوية لا تغير سلسلة النسخ الأساسية إن كانت لديك. لا نستخدم `WITH FORMAT` أو `INIT` تلقائيًا. خيار ضغط النسخ لم يفرض، لاختلاف إمكانات الإصدارات.

`VERIFYONLY` يتحقق من اكتمال النسخة وقابلية قراءتها وبعض ترويسات الصفحات والمجاميع الاختبارية، ولا يتحقق من بنية البيانات كاملة ولا يغني عن استعادة تجريبية. لا يحتوي النسخ الاحتياطي لقاعدة واحدة على جميع إعدادات الخادم أو Logins أو شهادات TLS أو `.env`. احفظ الإعدادات والسر والشهادات في وجهة آمنة منفصلة ومقيدة الصلاحيات. ملف النسخة يحتوي بيانات العملاء وتجزئات المصادقة، فلا ترفعه إلى مكان عام.

## استعادة تجريبية في قاعدة جديدة

أوقف عمليات الكتابة أثناء نافذة استعادة التشغيل. ابدأ دائمًا بقاعدة استعادة منفصلة، دون استبدال القاعدة الحالية:

```sql
RESTORE FILELISTONLY
FROM DISK = N'D:\SQLBackups\DailySales_20261028_230000.bak';
GO
```

انسخ أسماء LogicalName الفعلية التي ظهرت، ثم استخدمها بدل DAILYSALES_DATA وDAILYSALES_LOG أدناه، وعدّل المسارات لتوافق مجلد بيانات خادمك وصلاحياته:

```sql
RESTORE DATABASE DailySales_RestoreCheck
FROM DISK = N'D:\SQLBackups\DailySales_20261028_230000.bak'
WITH MOVE N'DAILYSALES_DATA' TO N'D:\SQLData\DailySales_RestoreCheck.mdf',
     MOVE N'DAILYSALES_LOG' TO N'D:\SQLData\DailySales_RestoreCheck_log.ldf',
     RECOVERY, CHECKSUM, STATS = 10;
GO
DBCC CHECKDB (DailySales_RestoreCheck) WITH NO_INFOMSGS;
GO
```

إذا احتوت القاعدة ملفات بيانات إضافية، أضف MOVE لكل ملف حسب FILELISTONLY. لا تستخدم `WITH REPLACE` دون إجراء استعادة تشغيل مدروس ونسخة أمان من الحالة الحالية.

شغّل نسخة منفصلة من التطبيق باتصال `DailySales_RestoreCheck`، وتحقق من آخر جلسة ولقطة إغلاق وكشف عميل وCSV. قد يلزم ربط مستخدم قاعدة البيانات بالـLogin الموجود في الخادم الجديد. أبقِ المستخدمين خارج النظام أثناء التحويل التشغيلي، ثم بدّل اتصال القاعدة بعد نجاح التحقق، مع إمكانية الرجوع للقاعدة الأصلية.

## سياسة متابعة مناسبة

حدد تكرار النسخ والاحتفاظ به وفق حجم العمل وقيمة البيانات؛ اختبر استعادة فعلية دوريًا. يمكن استخدام SQL Server Agent إن توفر، أو Windows Task Scheduler مع حساب خدمة مناسب وأداة SQL موثقة. لا توجد مهمة مجدولة مفعلة في هذه الحزمة. استرجاع نقطة زمنية يحتاج إعداد Recovery Model وسلسلة Log Backups مناسبة؛ لم يضف التطبيق إدارة لها.
