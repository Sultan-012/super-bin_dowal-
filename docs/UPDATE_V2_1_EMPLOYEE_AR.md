# تحديث واجهة الموظف 2.1 — دون فقدان البيانات

## التغييرات

- رقم فاتورة الشراء، ورقم فاتورة الدين، ورقم فاتورة تحويل مبيعات الوردية **اختيارية**.
- المرفق **اختياري** للشراء والدين والتحويل البنكي. الصيغ: PDF وPNG وJPG، حتى 5 ميجابايت لكل مرفق، وملف واحد لكل عملية.
- تبقى الأسماء والمبالغ والتفاصيل المالية الضرورية إلزامية بحسب نوع العملية. **رقم مرجع الحوالة البنكية** ورقم سند الإيداع ما زالا إلزاميين.
- يسمح بتسجيل عدة ورديات منفصلة للموظف في التاريخ نفسه مع استخدام رقم سند إيداع مستقل لكل وردية.
- زر «بدء وردية جديدة» يظهر فقط بعد تلقي تأكيد نجاح التسليم؛ يفصل معرّفات ومحتوى الوردية السابقة عن الوردية الجديدة.
- عند غياب تأكيد الشبكة لا يظهر زر بدء وردية جديدة؛ ينبغي إعادة التحقق باستخدام نفس مفتاح الإرسال لتجنب التكرار.
- مراجعة المدير لازمة قبل اعتماد المطابقة. إذا كانت أرقام الفواتير فارغة، لا يحاول البرنامج وصل حوالات بديون تلقائيًا.
- يمنع الخادم إعادة استخدام ملف رفع مملوك لحساب آخر أو وردية أخرى، وتحفظ المرفقات في PostgreSQL وتبقى قراءتها مقصورة على المدير.

## تحديث مشروع موجود (طريقة الحزمة الجزئية)

1. أوقف خادم Uvicorn. لا تُشغّل أكثر من نسخة من الخدمة أثناء الترقية.
2. خذ نسخة احتياطية من قاعدة البيانات المتصلة بالبرنامج، وتحقق من ظهور ملف النسخة بحجم غير صفري. **لا تعتبر قاعدة الاختبارات التي فيها وردية تجريبية قاعدة إنتاج.** كذلك احتفظ بنسخة من مجلد المشروع وملف `.env` في مكان آمن لا ترفعه لأي شخص.
3. فك `Bin_Doul_Employee_Update_v2_1.zip` إلى **المجلد الأب** لمجلد `Bin_Doul_Financial_System` الحالي، مع السماح باستبدال الملفات. سيضيف الملفات المعدلة/الجديدة فقط. لا يحتوي التحديث على `.env` أو ملفات الخطوط أو بيانات الموظفين أو قاعدة البيانات، ولا يحذفها.
4. من داخل **مجلد `backend`** نفّذ الترحيل باستخدام حساب PostgreSQL صاحب صلاحيات ALTER:

```powershell
.\.venv\Scripts\python.exe -m alembic -c shift_alembic.ini upgrade head
.\.venv\Scripts\python.exe -m alembic -c shift_alembic.ini current
```

النتيجة الحالية المتوقعة: `20261030_03 (head)`. يتضمن الترحيل إزالة قيد الوردية الوحيدة في اليوم وتخفيف قيود الأرقام والمرفقات **دون إسقاط الورديات السابقة**. الترحيل للأمام فقط.

5. من **جذر** `Bin_Doul_Financial_System` نفذ لبناء React من الكود الجديد:

```powershell
npm --prefix frontend ci
npm --prefix frontend run build
```

خطوة البناء ضرورية. الملفات `frontend/dist` الناتجة عن الإصدار القديم لا تعكس الواجهة الجديدة؛ بعد البناء شغل الخادم من جديد، ثم حدّث المتصفح بـ `Ctrl+F5`.

6. شغّل FastAPI مجددًا من مجلد `backend`:

```powershell
.\.venv\Scripts\python.exe -m uvicorn shift_app.main:create_app --factory --host 127.0.0.1 --port 8000
```

7. **اختبر على قاعدة اختبار مستقلة** قبل العمل الفعلي: ادخل وردية بشراء بلا رقم فاتورة ولا مرفق؛ أضف دينًا بلا رقم مع إجمالي ووصف؛ أضف حوالة برقم مرجع بنكي بلا رقم فاتورة، وجرب رفع PDF أو PNG في كل نوع. سلّم الوردية، واضغط «بدء وردية جديدة»، وسلّم وردية أخرى بتاريخ الصندوق نفسه **بسند إيداع مختلف**. تأكد عند المدير أن كليهما ظهر، وأجرِ المراجعة والمطابقة على بيانات الاختبار فقط.

## الاحتياطات الإنتاجية

- اختبر الترحيل أولًا على **قاعدة منفصلة مستعادة من نسخة احتياطية**. لا تشغّل تجارب مالية في قاعدة التشغيل الحقيقي.
- إذا كانت قاعدة `bin_doul` عندك تحتوي ورديات تجريبية معتمدة، فلا تستخدمها كقاعدة إنتاج نظيفة؛ استخدم قاعدة جديدة مثل `bin_doul_prod` وصلاحيات وإعدادات إنتاج مستقلة.
- للتشغيل عبر الشبكة الخارجية استخدم HTTPS، `APP_ENV=production` و`COOKIE_SECURE=true`، ومستخدم PostgreSQL محدود الصلاحيات ونسخًا احتياطية دورية قابلة للاستعادة.
- لا تجرِ حذفًا مباشرًا لسجلات مالية أو ملفات SQL يدويًا. اترك النسخ المعتمدة محفوظة مع سجل التدقيق.
- عندما يكون رقم الفاتورة فارغًا، لا يوجد تطابق آلي بين الدين وحوالة نفس الوردية؛ يجب أن يتحقق المدير من القيم ومصدر السداد قبل الاعتماد.

## حدود التحقق المنفّذ مع هذا التحديث

- اختبار Backend: **48 ناجحًا، 1 متجاوز** (اختبار PostgreSQL الاختياري يتطلب خادم PostgreSQL منفصلًا).
- اختبارات الترقية بقاعدة SQLite ملفية منفصلة تضمنت سجلات سابقة؛ بقيت السجلات محفوظة بعد ترحيل 2.1 وبقي منع تعديل السجلات المالية قائمًا.
- فُحصت صياغة ملفات React المعدّلة باستخدام مترجم TypeScript؛ **لم يُنفّذ بناء الواجهة الكامل هنا** لعدم توفر اعتماديات npm في بيئة العمل بدون شبكة.
- هذا التحديث لم يُثبَّت على قاعدة الإنتاج لديك. النسخ الاحتياطية واختبار تشغيل PostgreSQL على Windows والتحقق من واجهة المتصفح مطلوبة قبل الإطلاق.
